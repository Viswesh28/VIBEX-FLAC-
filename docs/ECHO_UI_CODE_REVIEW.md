# Echo-inspired UI and code-level review

Date: 2026-11-11. Reference: EchoMusicApp/Echo-Music, `DESIGN.md` and repository screenshots Home.png, search page.png, library.png, Apple inspired music page.png. Echo is GPL-3.0; no Echo source code or art was copied. UI code here was independently written. Existing VIBEX theme variables and light/dark palettes remain unchanged.

## Reference vs VIBEX
Echo's reference home uses a short app header, horizontally scrolling mood pills, prominent edge-peeking artwork, and rounded grouped rows with overflow menus. Search and library use rounded controls and grouped lists. The Apple-inspired player shown in the repository is an artwork-dominant full-screen layout; Echo also offers other player styles, so the screenshots are not a single universal appearance.

VIBEX uses a React/Capacitor shell with sticky header, VIBEX home mix, grouped track components and full-player tabs. It relies on its existing real Media3 or browser playback paths, and its different layout contains useful controls unavailable in the reference screenshot. This change adds a real-data artwork rail, changes the shape and grouping of existing rows, tabs and chips, and adapts the search field, player art and mobile chrome. Track and rail actions still invoke the existing player and menu; no provider or playback code was replaced. VIBEX's other sections, player styles and features are retained. This is a **partial visual adaptation, not an exact reproduction** of every Echo screen or the full-bleed player. Pixel-perfect parity was not established.

## Selection and gesture review
The old style prevented selection only on a small set of buttons, leaving headers and other WebView chrome selectable. Scoped `.vibe-app` selection/callout prevention now covers app chrome. Inputs, textarea, contenteditable and lyrics explicitly restore selection, so copying lyrics and editing text still work. This is CSS-level suppression, not removal of Android system text actions globally. Existing song long press opens a song sheet, and the same handler applies to featured artwork; movement, pointer cancellation, scrolling ancestors and unmount cancel the timer. WebView-specific long-press and selection behavior remains unverified on hardware.

## Ground-level findings (not inferred from an emulator)
1. `HomeView.jsx` runs separate cached real catalog searches for songs and albums, ranks songs locally, and previously rendered an ornamental hero with small album art rather than Echo's artwork-led carousel. The added rail reuses the ranked list, playList and SongSheet; no mock content or second source is introduced. It renders at most six extra `Cover` instances. `Cover` attaches an IntersectionObserver and visibility listener per instance; this adds overhead, but no frame-time impact has been measured.
2. `theme.css` contained thousands of lines and layered mobile overrides; selection rules covered only specific selectors, so ordinary headings remained selectable. Overrides are added at the end deliberately to supersede earlier mobile selectors without altering color tokens. This specificity approach has a maintenance cost and needs later consolidation with visual regression coverage.
3. Song rows use a native-feeling explicit overflow button and long-press controller (`ui.jsx`, `LongPressButton.jsx`, `long-press.js`). Before this change pointer movement canceled the timer, but scrolling a parent without a pointermove did not; capture-phase scroll cancellation is now added. More than one mounted controller adds one scroll listener each; this is bounded by rendered rows and requires performance measurement, not a claim of improvement.
4. `Player.jsx` retains seek, playback, codec selection, queue and lyrics tabs. Full-screen artwork-driven Echo layout is not implemented; changing the entire player without losing controls requires further careful work. Existing sync uses player position and supplied timestamps; existing touch/wheel follow suspension does not cover all keyboard/scrollbar input.
5. `Cover` asynchronously caches only native artwork, with IntersectionObserver and a fallback image glyph; source image failure falls back rather than inventing artwork. No image/provider endpoint was added. Scrollable rails can load extra covers and increase work. High-blur layers already exist in VIBEX; their actual cost and root cause of jank remain unmeasured.
6. Existing collection long-press menus only expose Open; share image/lyrics and on-device checks remain incomplete as documented in `VIBEX_INTERACTIONS_SHARING_LYRICS.md`. New visual treatment does not complete those outstanding features.

## Follow-up: implementation in the Android app, version 21
The prior no-APK note above describes the earlier iteration and is superseded here. Echo-inspired changes are now packaged in the VIBEX Android app. The home artwork rail uses current ranked catalog tracks; the existing mix/insights remain below quick picks. Search now puts its input before its heading, library tiles use grouped surfaces, and the classic player on narrow screens uses larger edge-to-edge artwork while retaining the existing transport, queue, lyrics, codec and network controls. Aurora and desktop retain their existing layouts. Styles use existing VIBEX color tokens; original logo and features remain. Song/album/artist/playlist content still comes from the existing model.
